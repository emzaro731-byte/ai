# AI API Server

Backend for a Flutter/Android AI app with client API keys and multimodal OpenAI features.

## Features

- Chat with any model available to the configured OpenAI account, including GPT-5 family models.
- Image generation.
- Text-to-speech audio.
- Video generation jobs and job lookup.
- API-key generation, validation, and revocation.
- `/api/models` returns the models available to the configured OpenAI account.

## Environment

```bash
npm install
cp .env.example .env
# Set ADMIN_SECRET and OPENAI_API_KEY
npm start
```

## Main API

All AI endpoints require `x-api-key` using a client key generated by the admin endpoint.

- `GET /health`
- `GET /api/models`
- `POST /api/chat` — body can include `model`, `input` or `messages`, plus model options
- `POST /api/images/generate` — body: `{ "model": "gpt-image-2", "prompt": "..." }`
- `POST /api/audio/speech` — body: `{ "model": "gpt-4o-mini-tts", "voice": "alloy", "input": "..." }`
- `POST /api/videos` — forwards video-generation job creation
- `GET /api/videos/:id` — retrieves a video job

Admin-only:

- `POST /api/keys`
- `POST /api/keys/revoke`

### Music

The audio route currently provides speech/voice audio. It does not pretend to provide a dedicated music-generation model when one is not available in the configured OpenAI API account. A separate music provider can be integrated later without exposing its secret to the Flutter app.

## Security

Never put `OPENAI_API_KEY` in the Flutter APK. Keep it on this server as an environment/hosting secret. Client apps should only receive the generated `ai_...` API key.

The current API-key store is in memory for the starter project. Production should move it to Supabase/Postgres so keys survive restarts.
